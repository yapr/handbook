# IssueとPull Request

[AI開発ポリシー](agent-policy.md)を共通の権限・公開基準とし、人間もAIもレビュー可能な単位で変更します。

## 粒度

- 1 Issue = 1目的。目的、対象、対象外、受け入れ条件、検証方法を明記します。
- 1 PR = 1責務。目的の達成に不要な変更を含めません。大きいIssueは依存関係付きの小さいIssueへ分割します。
- 変更は300行・10ファイル以内を目安とします。超過は警告であり、一律の失敗条件ではありません。
- 行数はbaseとのmerge-baseからの追加行数と削除行数の合計、ファイル数は同じ差分の変更ファイル数で数えます。
- 生成物・lockfileは目安から別扱いにできますが、総量と除外対象を記録し、レビューから除外しません。バイナリもファイル数に含めます。
- 超過時は分割案または分割しない合理的理由をPRに記載します。数値を隠すための分割はしません。

例として、最新のbaseを取得後、次で差分を確認します（baseがmain以外なら置き換えます）。

```sh
git diff --stat origin/main...HEAD
git diff --numstat origin/main...HEAD
git diff --check origin/main...HEAD
```

## 検証と記録

変更に応じて、対象リポジトリが定めるtest・lint・build・手動確認を行います。
不具合修正では再現条件を確認し、挙動を変える場合は必要な回帰検証を行います。
文書のみの変更ではMarkdown構造、相対リンク、差分、秘密情報・非公開情報の混入を確認します。

各検証には、コマンドまたは手順、対象コミット、成功・失敗・未実行、結果の要約を記録します。
未実行の場合は理由と残るリスクを明記します。環境不足・未接続・CI未設定を「成功」と記載しません。
ログやスクリーンショットに秘密情報を含めず、証拠は必要最小限にします。

push後もPRのhead SHAとCI結果を確認します。CIが未設定ならその事実を記録します。
修正後は影響する検証を再実行し、最新コミットに対する結果へ更新します。

## Draft PRの記載項目

初期提出はDraft PRとし、次の項目を含めます。

- 目的と変更後の動作、変更概要、対象外。
- 関連Issue・依存関係。ただし非公開Issueとの対応は非公開側に記録し、公開PRには一般的な目的だけを書く。
- 検証のコマンド・手順・対象コミットと結果、未実行項目と理由。
- 変更量、目安を超える場合の分割案または理由。
- リスク、公開可能性の確認結果、残る課題と必要な人間の判断。

説明は会話を読んでいないレビュアーにも分かるように書きます。
Issueのクローズは完了判断後に行い、Draft PR提出だけで完了扱いにしません。

## 人間レビューと承認

レビュアーは受け入れ条件、差分の責務、検証証拠、秘密情報、公開範囲、運用への影響を確認します。
AIによる自己確認は人間レビューの代わりにはなりません。
未解決の失敗や未実行項目は、影響と対応を確認できる状態にします。

マージ・本番公開・課金・データ削除は[承認の境界](agent-policy.md)に従い、人間の明示承認を待ちます。
Draft解除やCI成功だけを重要操作の承認と解釈しません。
