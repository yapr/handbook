# Product Lifecycle

ヤプルでは、完成してから公開するのではなく、**できるだけ早く外に出して学ぶ**ことを大切にします。

そのため、公開URLがあることと、Productとして成熟していることは別に考えます。

PoCでも公開して構いません。

むしろ、実際に触れるものを早く出し、使われ方や反応から学びます。

プロジェクトやProductの状態は、次のStageで表します。

| Stage | 定義 |
| --- | --- |
| `idea` | 構想段階。まだ作ると決めていない |
| `poc` | 仮説検証中。Product化するかはまだ決めていない |
| `alpha` | Productとして育てると決め、内部または限定された利用者が使い始めている |
| `beta` | 外部の実利用者に使ってもらい、価値や使われ方を検証している |
| `production` | 継続提供すると決め、本番運用している |
| `maintenance` | 本番運用中だが、新規開発より保守を中心としている |
| `deprecated` | Productとして存在しているが、終了を決めている |
| `archived` | 開発・運用を終了した |
| `discarded` | PoCなどの結果、Product化しないと判断した |

Stageは、売上金額やコード量ではなく、**そのProductを誰に、どの程度の責任を持って提供しているか**で決めます。

大まかな流れは次の通りです。

```text
idea
 ↓ 作り始める
poc
 ↓ Productとして育てると決める
alpha
 ↓ 外部の実利用者に使ってもらう
beta
 ↓ 継続提供すると決める
production
```

すべてのProductが `production` を目指す必要はありません。

PoCで学びを得て `discarded` になることも、役割を終えて `archived` になることも、正常な結果です。

## Stageと成果は分けて考える

「1円でも売上が発生した」は、とても重要な出来事です。

ただし、それ自体を `beta` の条件にはしません。

無料サービス、OSS、社内ツールなど、売上を直接目的としないProductもあるからです。

代わりに、Stageとは別にMilestoneやMetricとして成果を記録します。

たとえば、

```yaml
stage: beta

milestones:
  first_public_release: 2026-10-01
  first_external_user: 2026-10-05
  first_revenue: 2026-10-10

metrics:
  users: 12
  revenue_jpy: 1000
```

のように管理します。

特に次の出来事を大切にします。

- 初めて公開した
- 初めて自分以外の人が使った
- 初めて継続して使われた
- 初めて1円を稼いだ
- 初めて1万円、10万円、100万円を稼いだ

**作ったこと、使われたこと、稼いだことを、それぞれ別の事実として残す。**

そうすることで、PoCをたくさん作ること自体を否定せず、それが「届ける」「稼ぐ」まで進んでいるかも見えるようにします。
